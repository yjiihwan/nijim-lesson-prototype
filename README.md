## 1. 이게 뭔가요

니짐내짐 실서비스에 붙일 **«레슨 관리» 기능의 동작하는 명세서**입니다.
문서로 쓰면 30장이 될 규칙(예약 자격·수강 확인·정산 단가·환불·일시정지·반복 수업)을
**실제로 눌러 볼 수 있는 화면**으로 만든 것입니다.

- 역할 3개가 한 벌에 들어 있습니다 — **회원 · 선생님 · 센터**
- 데이터는 **브라우저 메모리**에만 있습니다 (`data.js` 의 `window.DB`). 새로고침하면 초기화됩니다.
- 서버·DB·인증·결제가 **없습니다**. 일부러 안 만들었습니다 (→ §4, §5)

> 🔴 **이건 «옮겨 붙일 코드»가 아니라 «읽을 정답지»입니다.**
> 화면 코드를 그대로 복사하지 마시고, **규칙과 계산식**을 가져가세요.
> 어떤 규칙이 왜 그런지는 전부 코드 주석에 근거와 함께 적어 뒀습니다.

## 2. 왜 이렇게 만들었나요

니짐내짐 실서비스에는 이미 회원·멤버십·결제·강사가 돌고 있고,
강사 정산의 최종 확정 권한은 **샐리(Sally)** 에 있습니다.
레슨 모듈이 새로 책임질 것은 **«수업이 실제로 있었는가»라는 사실**까지이고,
**«그래서 얼마를 주는가»는 샐리 몫**입니다. 이 경계를 흐리지 않으려고

- 배분율·공제·급여명세를 **일절 계산하지 않습니다** (화면은 «정산 대상 금액»까지만 말합니다)
- 회원·직원·결제 마스터를 **소유하지 않는 것이 목표**입니다
  (프로토타입은 데모를 위해 임시로 들고 있을 뿐입니다 → §4 C2·C3·C5)

### 왜 한 파일인가요 (쪼개지 않은 이유)

일부러 그대로 뒀습니다. 근거는 셋입니다.

1. **모듈 레벨 가변 상태가 31개** 있고 219개 함수가 한 클로저로 공유합니다.
   모듈로 쪼개면 이 상태를 전부 export/import 로 바꿔야 하고, 한 곳만 놓치면
   «조용히 다른 인스턴스를 보는» 버그가 납니다 — 이관 전에 심을 위험이 아닙니다.
2. **인라인 `onclick="App.***"` 가 276곳** 있습니다. 전역 `window.App` 이 전제입니다.
3. **«빌드 불필요»가 설계 목표**입니다. 번들러를 끌어들이면 받는 쪽이 정답지를
   실행해 보기가 오히려 어려워집니다.

대신 **구역 배너 + 상단 색인 + 함수별 입력/출력/불변식 주석**으로 길을 냈습니다.
어차피 여러분은 이 파일을 «실행할 코드»가 아니라 «읽을 정답지»로 쓰시게 됩니다.

## 4. ⚠️ 주의 3가지 — 이것만은 꼭

### ⚠️ 주의 1. «멤버십»이라는 단어가 실서비스와 뜻이 다릅니다

이 프로토타입에서 «멤버십»은 **회차제 수강권**(`DB.passes` — 20회권·10회권)입니다.
실서비스의 «멤버십»은 **기간제 시설 이용권**입니다. **화면 라벨만 일부러 같게 썼습니다.**

> 🔴 **두 테이블을 합치지 마세요.** 합치는 순간 잔여 회차·회당 단가·정산이 전부 오염됩니다.
> 새 테이블 `lesson_passes` 를 만들고 실서비스 `membership` 은 그대로 두세요.
> (같은 함정이 «일시정지», «회원», «강사», «결제» 에도 있습니다 — **인계 스펙 §1 충돌면 29건**을 꼭 보세요.)

### ⚠️ 주의 2. 프론트가 계산하는 것을 그대로 옮기면 그 자리가 곧 취약점입니다

이 프로토타입은 **금액·잔여 회차·권한·중복 예약·만료일을 전부 브라우저에서** 판정합니다.
데모니까 괜찮은 것이고, 실서비스에서 그대로 두면 브라우저 콘솔 한 줄로 뚫립니다.

```js
DB.me.member = "m999"      // → 남의 계정으로 수강 확인·이의제기
DB.passes[0].remaining = 999  // → 무제한 예약·차감 → 그만큼 정산 라인 생성
DB.slines[0].pushed = false   // → 이미 보낸 정산을 다시 전송(이중 지급)
```

👉 **`[SERVER]` 로 검색되는 40곳이 «서버가 권위를 가져야 하는» 자리**입니다.
각 마커에 어떤 API·트랜잭션·잠금이 필요한지 한 줄로 적어 뒀습니다. 하나도 빠뜨리지 마세요.

### ⚠️ 주의 3. 프로토타입 한정 «가짜 동작»을 진짜로 옮기면 최악입니다

| 프로토타입의 가짜 동작 | 실서비스에서는 |
|---|---|
| 메모리 DB · 새로고침하면 초기화 | RDB + 트랜잭션 |
| **«자동확정 시한(n시간) 경과» 버튼**(«시뮬레이션» 상자) | 서버 크론(스위퍼 S1) |
| **«이의기간 경과» 버튼**(«시뮬레이션» 상자) | 서버 크론(스위퍼 S2) |
| **«회원 폰 화면 열기» 버튼**(같은 브라우저에서 QR 랜딩을 연다) | 회원이 **본인 폰 카메라**로 스캔 |
| 반복 회차를 **부팅 때** 8주치 생성 | 매일 04:00 KST 배치 (멱등) |
| 결제 버튼 누르면 즉시 수강권 생성 | PG 결제창 → **결제 성공 웹훅**에서 서버가 생성 |
| 「샐리로 보내기」가 로컬 플래그만 세움 | 샐리 API 호출 + 멱등키 + 회수 규칙 |
| 역할을 URL 해시로 고름 (`#/c/...` 치면 센터 화면) | 서버 인가(RBAC) |

👉 전체 목록과 «무엇으로 대체하나»는 **인계 스펙 §5 미구현·의도적 생략 33건**에 있습니다.
특히 **«일부러 안 만든 것»**(월마감·공휴일 자동 제외·겹침 차단 등)은
빠뜨린 게 아니라 **확정된 결정**이니 임의로 추가하지 마세요.

## 5. 실행 방법 (3가지 중 아무거나)

```bash
# ① 그냥 열기 — 가장 빠릅니다
open index.html            # macOS
start index.html           # Windows

# ② 로컬 서버로 열기 (권장 — file:// 제약이 없습니다)
python3 -m http.server 8791
# → http://localhost:8791/

# ③ 배포본 (설치 없이)
# https://yjiihwan.github.io/nijim-lesson-prototype/
```

**체험 계정은 없습니다.** 로그인이 없어서 첫 화면에서 **역할을 고르면** 바로 들어갑니다.

| 역할 | 기본 계정 | 권장 뷰포트 | 첫 화면 |
|---|---|---|---|
| 회원 | 김지은 (`DB.me.member = "m1"`) | **모바일 390px** | `#/m/home` |
| 선생님 | 박준형 (`DB.me.teacher = "t1"`) | **모바일 390px** | `#/t/home` |
| 센터 | 엔짐 개봉점 (`ct1`) | **PC 1440px** | `#/c/home` |

> 역할을 바꾸려면 화면을 나갔다 랜딩(`#/`)에서 다시 고르면 됩니다.
> 다른 회원으로 보고 싶으면 콘솔에서 `DB.me.member = "m2"; App.render?.() || location.reload()`.
> 🔴 이렇게 «콘솔 한 줄로 남이 될 수 있다»는 것 자체가 §4 주의 2가 말하는 문제입니다.

**직접 눌러 볼 시나리오 10선**(클릭 순서까지)은 인계 스펙 v2 §7 에 있습니다.
예약 → 출석 → 수강 확인 → 정산 전송 → 회수까지 한 번 돌려 보시면 구조가 한눈에 들어옵니다.
